# live-meeting-minutes

会议进行中实时转写，并基于持续更新的上下文滚动生成结构化纪要。**全本地运行，不调用任何云端 API。**

对标飞书妙记的实时纪要能力，但数据不出本机。

---

## 为什么是自己搭，而不是找现成项目

调研过一圈开源方案（Meetily、Speakr、ownscribe、Ollama-Transcriber 等），它们都是**会后总结**：录完 → 转写 → 丢给 LLM 出纪要。没有一个做"边开边滚动更新纪要"。

滚动摘要这一层不难，难的是别把它做成会爆的形态。见下面的设计决策。

---

## 架构

```
声卡 (WASAPI loopback / 麦克风)
  --> 采集 16k s16le PCM，自动增益
  |-> meetings/<id>/audio.wav      边开边录，落盘
  --> WhisperLiveKit + Qwen3-ASR   (ws://localhost:8000/asr)
  <-- 持续回传转写行（带时间戳）
  --> 切句 + 插值时间戳            --> meetings/<id>/transcript.json
  --> 增量抽取 + 有状态合并
  --> 本地 LLM                     (OpenAI 兼容端点，LM Studio / llama-server)
  --> live_minutes.md              持续覆盖刷新
  --> meetings/<id>/minutes.md     会后归档
```

三个进程：摘要模型（LM Studio 或 `llama-server`）、`wlk`（转写服务）、本程序（采音频 + 编排 + 归档 + 界面）。

每场会议归档成一个目录，录音、带时间戳的转写、纪要都在里面，界面里可检索、回放、导出。

### 两个界面，一套编排

编排逻辑在 `engine.py`，界面只是它的一个消费者：

```
engine.Engine(sink)
  ├── desktop.py   PySide6 桌面应用（默认入口）  sink -> Qt 信号
  └── app.py       网页控制台（备选）            sink -> WebSocket
```

`sink` 只需实现 `broadcast(event)` 和 `log(text, level)` 两个方法。当初做桌面版时差点把
编排复制一份，两份一定会漂移，所以抽了出来。

## 设计决策

### 1. 摘要用「抽取 + 有状态合并」，不做全量重摘

朴素做法是每隔几分钟把全部转写重新喂给模型总结。这条路必然翻车：

- 上下文随会议时长线性膨胀，开一小时就爆
- 每轮整篇重写，纪要内容来回跳，人没法边看边用

改成两步、有状态：

1. **抽取**（频繁、便宜）— 只把**新增的那一段**转写喂给模型，抽出原子要点，分成议题/决议/待办/风险/待确认问题五类
2. **合并**（低频、受约束）— 把当前纪要条目列表（只有 id + 一句话）和新要点一起给模型，让它对每条判断 `add` / `merge` / `update`，**操作在本地代码里执行**

结果：送进模型的上下文长度**恒定**，会开三小时也不涨；条目 id 稳定，纪要只增不乱排。

合并步骤本质是"这两句说的是不是同一件事"的判断题，小模型完全扛得住，比让它写整篇纪要靠谱得多。

### 2. 背压：宁可粒度粗，不能让纪要落后

会议不会等模型。生成速度一旦跟不上说话速度，队列开始堆积就**永远追不回来**，最后屏幕上是二十分钟前的内容。

积压超过 `--max-pending` 就把待处理片段合并成一条送进去。

### 3. 音频必须由本脚本采集

WhisperLiveKit **每个 WebSocket 连接是独立会话，服务端不广播转写**。所以不能"浏览器采音频 + 脚本旁听"，脚本必须自己当那个唯一的客户端。

且必须走 **WASAPI loopback 采系统输出**——只采麦克风的话只能录到自己说话，别人的发言全丢，纪要就没意义了。

### 4. 宁可换小模型，也不要低比特的大稠密模型

8GB 显存下的直觉是"把模型量化得更狠一点"，这是错的。

稠密模型每生成一个 token 都要把全部权重过一遍。Qwen3.8-27B 的 Q4_K_M 是 17GB，塞不进 8GB 显存，大部分在内存里，每个 token 都得从内存搬一遍——被带宽焊死，实测 5-6 tok/s。降到 3bit 是 12-13GB，**仍然塞不进 8GB**，还在搬，所以治不好，还白白搭上了 JSON 指令遵循能力（这条流水线唯一依赖的能力）。

出路有两条，都试过了。一条是 **MoE**：注意力、路由器、共享专家留显存，路由专家扔内存交给 CPU，每 token 只激活一小部分——Qwen3.6-35B-A3B 总量更大（18GB）却更快。但 8GB 卡上它和语音模型抢不过，可用内存被压到 0.8GB。

另一条是**直接换小模型**，最后走的是这条。这个任务是 schema 约束下的结构化抽取，不吃推理深度：模型从 35B 降到 2B，一轮从 18.4 秒降到 2.6 秒，分类和 `owner` 填充的正确性没有可见损失。代价是决议识别变弱（见 [SETUP.md](SETUP.md) 的选型经过）。**先想清楚任务吃不吃推理深度，再决定省在哪。**

### 5. 显存优先给 ASR

纪要质量的上限由转写质量决定。转写错了，再强的摘要模型也只是把错误总结得更工整。

### 6. 采集端加自动增益

**转写碎成单字，八成是电平不是模型。** 笔记本麦克风阵列采到的语音峰值实测只有满幅的
5%–22%，转写会退化成「嗯。 那边。 这样。 天。」这种碎片，看起来像模型坏了或者内存不够。

排查时逐个证伪过：内存还剩 4.7 GB、显存剩 2.7 GB，不是资源问题；44100Hz 走的非整数重采样
路径没有抗混叠，但 A/B 测下来和 48000Hz 质量一致，不是重采样；摘要模型持续满载时转写结果
与空闲时**逐字相同**，不是 GPU 争抢。最后把同一段录音只改增益重放，x1 碎片、x6 成句、
x14 完整——是电平。

所以采集端加了包络跟随的自动增益（`audio.AutoGain`）。loopback 采系统输出本来就接近满幅，
增益会自动停在 1 倍，开着没有副作用。

### 7. 转写要自己切句

WhisperLiveKit 只在换说话人或长静音时才另起一行，同一个人连讲两分钟就是一整行。不切句有
两个后果：展示成一大块没法读，以及**摘要永远触发不了**——「已确认文本」按行取的话，一个人
连讲十分钟都攒不出一次抽取，实时性就没了。所以按句末标点切开，再按字符占比在该行的
`[start, end]` 里插值出每句的时间戳。

> 时间戳字段是 `start` / `end`，值是 `"0:00:23.29"` 这种字符串而不是秒数。

## 硬件基线

开发机：RTX 5070 Laptop (8GB) + Ryzen AI 9 HX 370 + 32GB RAM + Windows

两个模型同时加载、整条流水线跑起来时的实测占用（`nvidia-smi` / 任务管理器）：

| 项目 | 显存 |
|---|---|
| 显存总量 | 8151 MiB |
| Qwen3-ASR-0.6B + MiniCPM5-2B (Q8_0, ctx 8192) + Windows 桌面 | 5159 MiB |
| **余量** | **2733 MiB** |

内存 32GB，同时跑两个模型 + 浏览器时余 4.7 GB。够用但不宽裕，开会时别挂一堆 Chrome。

> 换回 4B 或更大的模型时，显存余量会迅速见底——语音模型那 2–2.5 GB 是不能动的（见下条）。

## 运行

**双击 `启动.bat`**，桌面应用打开，选好声音来源点「开始」。

安装步骤见 [SETUP.md](SETUP.md)。

界面会拉起并托管另外两个进程（转写服务、摘要模型），左边实时转写（逐句带时间戳），右边滚动纪要，底部是三个进程的日志。

不想要桌面窗口就跑 `python app.py`，网页控制台在 http://127.0.0.1:8500，功能一致。

纪要同时写到 `live_minutes.md`，用原子替换写入，拿 Markdown 编辑器开着实时预览不会读到半截文件。

### 会议归档与历史

点「开始」就新建一场会议，点「停止」封档。每场一个目录：

```
meetings/20260909-143025/
    audio.wav          16kHz 单声道，边开边写
    transcript.json    逐句转写，每句带起止时间
    minutes.md         纪要
    minutes.json       结构化纪要
    meta.json          标题、起止时间、时长、句数、条数
```

右上角「历史」进归档：按标题、**转写原文、纪要内容**全文检索，点开可回放录音、切换「纪要 / 转写原文」、改标题、删除，导出 `.md`（纪要）/ `.txt`（带时间戳的转写）/ `.json`（全部）。

桌面版里**双击转写的某一句，录音会跳到那个时间点**——这是选 Qt 而不是继续用浏览器的主要原因。

没说话就停止的空会议会被自动丢弃，不会堆进列表。

> `meetings/` 已在 `.gitignore` 里——它装的是真实会议内容，和 `live_minutes.md` 一样绝不入库。

### 文件结构

```
启动.bat          双击入口
desktop.py        桌面应用（PySide6）——默认界面
engine.py         编排核心：进程托管、采集、转写切句、归档。界面无关
app.py            网页控制台（备选界面），与桌面版共用 engine
minutes.py        纪要状态机、提示词、抽取与合并
meetings.py       会议归档：录音写入、检索、导出
audio.py          设备枚举、WASAPI loopback 采集、自动增益
web/index.html    网页控制台页面（无构建步骤，原生 JS）
config.json       所有可调参数
live_minutes.py   早期的纯命令行版本，不做归档，不走 engine
```

## 调 `--n-cpu-moe`

`--n-cpu-moe N` 把前 N 层的路由专家挪到 CPU，只挪路由专家，注意力和 KV 不动。

性能随 N 是 **V 形**：塞不下时惨不忍睹，在"刚好放得下"的最小值最优，再往上缓慢下滑。有人在 5090 上实测 20 档 54 t/s、16 档 64.5、12 档 69.4，再降一档掉到 27.5。

**崩塌是无声的，不报错，只是突然变慢。**

从 32 往下减 2，减到显存溢出退回一档。

> **先把 ASR 服务起起来再调。** 对着空显存调出来的最优值，等 ASR 一加载就直接掉进悬崖，而你只会看到摘要莫名变慢，查不到原因。

### ⚠️ 一个会直接踩进去的坑

网上教程普遍推荐的这条命令：

```
--qwen3-streaming-tower-checkpoint qfuxa/qwen3-asr-0.6b-streaming
```

**是纯英文的。** 那个 tower 用 LibriSpeech 自蒸馏成因果块结构，作者自己写明了代价：中文 CER 从 11.4 崩到 **85.7**，法语 WER 从 7.8 崩到 37.9。

**中文场景不要加这个参数**，保留原生多语言 tower 走 windowed 模式（默认，准确率也更高：live WER 12.6 vs 因果模式 17.6）。

如果 windowed 模式中文确实不行，退路是 [Qwen3-ASR-1.7B](https://huggingface.co/Qwen/Qwen3-ASR-1.7B) + vLLM 原生流式（官方明确流式只在 vLLM 后端可用，52 种语言含 22 种中文方言），需要重写 `receive_transcript` 对接其协议。

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--device` | 自动 | 音频设备编号，`--list-devices` 查 |
| `--loopback` | 关 | 采系统输出而非麦克风，**录别人发言必须开** |
| `--min-chars` | 180 | 攒够多少字触发一次抽取 |
| `--max-wait` | 45 | 最多等多少秒必定触发，冷场也出结果 |
| `--max-pending` | 2 | 积压超过此数就合并片段 |
| `--overview-every` | 4 | 每 N 轮重写一次概述，0 关闭 |

模型慢就把 `--max-wait` 提到 60，比让队列堆积好。stderr 里持续出现 `[背压]` 就是这个信号。
